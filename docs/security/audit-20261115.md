## 0. 要旨

- **細工した入力 1 つで利用側のアプリが落ちる経路が多数残っている**（W1〜W11・W15・W16）。どれも Swift の trap かスタックあふれで、
  `try?` では受けられず、**`limit:` を渡していても、`info()`・`folderUnpackSizes()` で前もって調べても防げない**。
  `sy.3`〜`sy.12` は、ファジングと利用側の点検で見つかった箇所を塞いだが、Deflate のブロックの境目・GZip の拡張欄・BZip2 の表・
  LZMA の確率表・XZ のブロックヘッダには届いていなかった。**ZIP は上流のまま範囲の検査が一つも無い**（ただし利用側は ZIP を使っていない。§3）。
- **W6 は細工すら要らない**: `xz --lzma2=pb=4`（Python の `lzma` で作った 256 KB の普通の .xz でも）の**正規のファイル**で
  `XZArchive.unarchive` が落ちる。上流のコードの確率表の大きさの誤り（432 要素で、添字 432 を使う）。
- **解析だけでメモリ・時間が際限なく増える**もの（W12〜W14）は、利用側が検査に使う `info()`・`folderUnpackSizes()` 自体の中で起きる。
- fork が足したもの（BCJ・高速経路・進捗・`limit:`）に由来するのは W26・W27・W29・W30 と低の一部。残りは上流由来。

## 2. 直し方の案（第2段の時点の案。直した結果は §1 の「状態」）

- **trap の群（W1〜W11・W16）**: 7z・TAR に入れた堅牢化（`sy.3`〜`sy.11`）と同じ型で、読む前に残りを確かめて throw する。
  W1 はブロックのループの頭に `guard bitReader.bitsLeft >= 3`、W2 は subfield の頭に `guard xlen >= 4`、W3 は `selectorsCount >= 1`、
  W4 は内側のループの後でも `1...20` を検査し、`DecodingTree` の前に `maxBits <= 20`（Deflate は 15）、W6 は確率表を 433 要素に
  （か isRep 以降を 192 から詰める）、W7 は `rep0 >= dictEnd` で throw し `byte(at:)` の折り返しを消す、W8 は liblzma と同じく
  「最初の chunk は辞書のリセット・props 未設定の LZMA chunk は throw」、W9 はヘッダを `realBlockHeaderSize` ちょうどの部分 `Data`
  から読む、W10 は `bytesLeft >= paddingSize`、W11 は大きさを `UInt64` で読み `UInt64.max` 以外の `Int.max` 超を throw、
  W16 は ZIP の各構造の入口で範囲を確かめ、`UInt64` → `Int` は `Int(exactly:)`。
  **回帰試験は、この repo に足す**（今は利用側のアプリにだけある。README "Verification"）。上の実測の入力（§1 の「確認」の列）がそのまま使える。
  W6 には pb=4 の正規のファイルを足す。
- **再帰（W5・W15）**: ループにする（`multiDecompress`・`TarParser` と同じ形）。
- **解析の資源（W12〜W14・W25・W28）**: 7z は `numFiles`・`numFolders`・`numPackStreams`・substream の合計に絶対の上限（例 1<<20〜1<<22）、
  0x0E〜0x15 の性質の重複を断り、空ストリームの数は 0x0E で一度だけ数える、folder の stream の**合計**を 64 まで、pack stream の
  位置は累積を一度だけ計算。TAR は PAX のヘッダの大きさ（例 1 MiB）と未知のレコードの数に上限を置き、global と local を合成して
  エントリごとに持たせない。
- **上限（W17〜W19・W22・W23・W26・W29・W30）**: ZIP の Deflate・BZip2・LZMA に宣言サイズを `limit` で渡し、`ZipContainer.open(container:limit:)`
  を足す。重なったエントリと data descriptor の食い違いを断る。W18 の各 API に `limit:` 版を足す（multi 系は合計で）。W19 は上限付き版で
  末尾が残れば throw する（か、全部をつないで合計に上限）。W26 は folder の展開を 1 回だけにし、長さを `folder.unpackSize()` と照合。
  W29 は `reserveCapacity(min(expecting, 64 << 20))`。W30 は範囲デコーダが埋めた 0 の数を数えて throw。
- **W21**: 切り出しと読み飛ばしの両方に PAX の size を使う（POSIX のとおり）。`TarReader` も揃える。
- **W27**: `UInt32(truncatingIfNeeded:)`。
- 修正後は、利用側 4 アプリの `exact:` を新しい tag に上げる（`VENDORED.md` §4 の 7）。版を上げるだけでは、W18 の新しい API は使われない。

  ある（W3・W4・W12〜W14 ほか）。悪意のある書庫を受け取ることが前提で、攻撃を受けた兆候は無い。直す順は、自動で届く W3・W4・W14・W12・W13、
